# 一个退款冲突，怎样显露更大的关系问题？

[English](./refund-conflict-recursion.md) · [整体与递归导读](../whole-system-and-recursion.zh-CN.md)

这是合成教学例，没有真实企业、订单或金额，不执行退款，不是CASE005实际运行记录。下述判断是设计预期，本例固定输入、输出和测试均未执行。

## 场景：承诺先发生，依据尚不完整

平台条款说满足条件A可退款；商家规则说该类订单均不退款。条件A缺少证据，客服AI却已经承诺退款。

一个人可能问“客服是否越权”，另一个人问“审批为什么跟不上”，组织负责人问“部门是否长期使用不同规则”。这些是同一事件的不同关系问题，不是谁更高级就更接近真相。

本例把客服主体叫L1、客服与退款协作体叫L2、企业叫L3、独立企业间网络叫L4。它们只是本次边界中的尺度，不是四个必经步骤。形成的整体仍可作为更外层节点，成员不因此失去边界。

## 局部：不知道就留下不知道

Observer组织获授权的对话和订单事实；KG绑定规则来源、版本、适用范围及冲突；Protocol说明承诺权限和责任；Engine在支持的Profile下计算。

设计上应保留条件A为UNKNOWN、规则冲突、承诺可能越界及人工复核需求。UNKNOWN不是零风险，也不是自动拒绝或批准退款。具体输出取决于责任仓合同，不能凭故事声称已经计算。

结果与依据分别留存。符石可关联本次结果及证据，但不是全部原文或退款许可。

## 协作关系：个体正常，连接处仍可能有问题

L2引用获准的下层结果、证据、未知与复核限制，另加入交接关系、审批权限、队列和规则传播时间。

“客服可立即承诺，但审批无法及时核实”可能构成关系风险。多个正常个体的平均分不能回答这个问题，一次异常也不能证明协作体整体失效。

客服、退款审批、知识发布之间还可以横向交换获准引用。规则发布更新而缓存未同步，会在连接处产生冲突；不必先向上汇报才能看见关系。

## 组织：补入自身事实，再形成自己的判断

L3加入部门制度、资源、责任锚和规则发布历史，问承诺、预算、法务与知识发布是否一致。风险可能来自生效时间理解不同，而不是员工必然有错。

这是本层重算，不是复制下层报告或升级标签。上层结论不同不覆盖下层旧结果，也不能自动向下归责或下发业务动作。

跨企业联合复核还须明确身份、授权、互认、可见性和交换合同；内部通过不等于外部互认通过。门禁缺失则停止相应路径，不因写着L4就进入真实网络。

## 谁决定，谁保留记录？

| 问题 | 本例的边界 |
|---|---|
| 谁决定退款？ | 有实际退款权限的责任主体；业务系统在获授权范围内执行 |
| 谁修规则？ | 有规则修改权限者；批准生效又是另一项权限 |
| 谁能看原文？ | 按每条引用的可见性核对；上层不天然拥有全部数据 |
| 谁证明发生了什么？ | 经明确合同留存的Evidence、Audit、Replay和复核记录；Observer承担其支持范围内的证据职责 |
| 谁能从报告取得权限？ | 没有人；报告、符石和计算结果不签发行动权 |

实际企业须提供授权矩阵、额度与条件、交接和冲突暂停流程、规则生效时间与旧交易适用条件。故事不能替企业决定“这张单谁批”或“旧订单用哪版规则”。

## 回查与反馈，不改旧账

从组织主张追到获准下层结果，再核对时间、版本、证据引用和权限。无原文权限就使用获准视图或停止；连存在性披露也可能受限。

补齐条件A或发现规则错误后，追加新证据、固定新快照并按本层合同重新运行。若推翻旧判断，更正须关联旧结论、依据、适用时间和复核者。历史记录仍保留。

反馈还可能支持规则校准或制度调整的建议，但修改规则、批准生效和业务行动都需各自授权。复算通过不自动批准行动，也不是自动学习或覆盖历史。

## 三位一体怎样进入这个例子

数据依据是获授权的业务事实与规则，不假装用了文明天气。流程方法帮助定位、核查依据、分析关系传导和可能后果。元层要求分析者声明位置与利益，检查客户、客服、复核者承担的影响与盲区，接受补充校准。

不同报告可以分别关注客服交接、财务敞口或组织负担，但不得删除关键UNKNOWN与反证。报告不替代结构化计算。

## 能与不能说明什么

本例解释局部循环、横向关系、跨尺度重算、证据回查和反馈，不能证明自动跨层Context、统一回钻、Loss Certificate或完整L1—L4运行时已经实现。也不证明具名企业采用、一般兼容或生产就绪。
